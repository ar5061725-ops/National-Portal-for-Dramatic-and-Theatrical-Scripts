1. المرحلة الأولى: التحويل من HTML إلى Next.js

  1. تحويل شاشات التصميم الثابتة إلى تطبيق Next.js 15 (App Router) + React 19 + TypeScript، بواجهة عربية من اليمين لليسار تُصمَّم للجوال أولاً.
  2. اعتماد CSS Modules وألوان وهيكل التصميم المعتمد في المستند المرجعي.
  3. بناء مكوّنات قابلة لإعادة الاستخدام: Button, TextField, Card, StatePanel, SegmentedControl, PageHeader, PageBody, BottomNav, Form, FormError.
  4. تنظيم المسارات بمجموعات: (tabs) للتبويبات السفلية، (flow) لمسارات الخطوات (تقديم، دفع)، (print) للطباعة والتحقق.
  5. الاعتماد على مكوّنات الخادم مع «جزر» عميل صغيرة، وخطاف useAsyncAction لحالات التحميل والنجاح والخطأ بشكل موحّد.
  6. إنشاء طبقة src/lib/api لعزل منطق الاتصال عن الواجهات (قابلية التوسع والصيانة).

2. الواجهة وتدفق الاستخدام

  1. صفحة بداية (Splash) قبل التسجيل: تعريف بالبوابة وثلاث خطوات (أنشئ حسابك، قدّم نصك، تابع التقييم) وزر تسجيل الدخول.
  2. تسجيل الدخول / إنشاء حساب بتبويبين، مع حقول الهوية (الرقم المدني، تاريخ الميلاد…) ودليل إرشادي إلزامي قبل المتابعة.
  3. تدفق الدخول: بداية ← تسجيل ← الرئيسية. الموقع كله يتطلب تسجيل الدخول ويظهر الشريط السفلي بعده.
  4. دخول اللجنة منفصل (/committee/login) ولا يوجد تسجيل ذاتي للمراجعين.
  5. إصلاح تاريخ الميلاد: الحقل الأصلي كان يعرض نصاً عربياً معكوساً، فاستُبدل بثلاثة حقول رقمية (يوم/شهر/سنة).
  6. إصلاح عرض الاسم الكامل المقصوص (دالة rpad كانت تقتطع الاسم إلى حرفين) بترحيل قاعدة بيانات وإصلاح البيانات القائمة.

3. الخلفية: Supabase

  1. إنشاء المشروع وجداول المؤلفين والطلبات والملفات والتقييمات والإشعارات مع سياسات أمان الصفوف (RLS).
  2. دوال RPC بصيغة SECURITY DEFINER مع search_path=''، ومخطط app_private للجداول الداخلية.
  3. أدوار المستخدمين: author وreviewer وcommittee_manager.
  4. جدول author_identity لحفظ بيانات البطاقة المدنية في جدول مغلق، وبوابة هوية تُلزم باستكمال البيانات (/account/identity).
  5. سلال التخزين (submissions-portal وغيرها) لرفع ملفات النصوص بصيغة PDF.
  6. مهام مجدولة: pg_cron وpg_net لتسوية المدفوعات كل دقيقتين.
  7. ترحيلات قاعدة البيانات 20261115000007 إلى …14: جولات التقييم، أنواع النصوص، هوية المؤلف، بحث الدفع والرسوم، محاولات الدفع المعلّقة، إصلاح اقتطاع الأسماء، قوائم المشرف، منع إعادة الإسناد بعد التعارض.

4. المصادقة والحماية

  1. عميل @supabase/ssr بملفات الارتباط، مع middleware يحجب الصفحات غير العامة ويتحقق من الأدوار وبوابة الهوية.
  2. الصفحات العامة فقط: / و/login و/committee/login و/reset-password و/verify/* و/auth/*.
  3. ثغرة وُجدت وأُصلحت: المطابِق كان يستثني أي مسار فيه نقطة فيمكن تجاوز الحماية (مثل /submissions/new.x)، فضُيِّق المطابِق.
  4. مسار /auth/confirm يستقبل token_hash فتعمل روابط البريد من أي جهاز (استعادة كلمة المرور تفتح صفحة التعيين، والتأكيد يعيد لتسجيل الدخول).
  5. استعادة كلمة المرور: مهلة 60 ثانية لمنع التكرار، ورسائل خطأ عربية واضحة، وشاشة تعيين كلمة جديدة (ResetPasswordForm).
  6. قوالب بريد عربية (supabase/email-templates) وإرسال عبر Resend SMTP. وضع الاختبار يرسل فقط إلى بريد صاحب الحساب، ويلزم توثيق نطاق قبل الإطلاق.
  7. ترويسات أمان ونهج CSP في next.config.mjs (مع السماح بـ unsafe-eval في التطوير فقط)، ومراجعة موثّقة في SECURITY-REVIEW.md.
  8. تغيير بريد حساب المؤلف إلى ar5061725@gmail.com مع الإبقاء على بيانات الهوية.

5. آلية تقييم النصوص (وفق ملف «آلية تقييم النصوص»)

  1. نموذج تقييم v1 بثمانية معايير موزونة: الإجمالي = مجموع (الدرجة × الوزن) ÷ 10.
  2. عتبات القرار: 80 و65، وفرق 15 بين المراجعين يستدعي التحكيم ثم الوسيط.
  3. تسجيل القرار (record_decision) ثم نشر النتيجة (publish_review_result) كلقطة لا تتغير.
  4. شاشات اللجنة مربوطة بالبيانات: CommitteeReview وRoundDecision وAssignReviewerPanel وCriterionField وNoteEditor وDecisionPicker.
  5. إقرار تعارض المصالح من المراجع، ومنع إعادة إسناد النص بعد التعارض.
  6. مراجعة تجريبية فعلية انتهت بنتيجة 76.5، وإسناد وقرار ونشر من حساب المشرف.

6. الدفع (MyFatoorah تجريبي)

  1. رسوم التقديم 10.000 د.ك لكل نص، وتُقرأ من قاعدة البيانات.
  2. دالة Edge payment-create (تتطلب JWT) تُنشئ الفاتورة وتُرجع رابط الدفع؛ والمفاتيح في أسرار Edge وملف .env.local فقط.
  3. التأكيد بطريقتين دون تسجيل ويبهوك: صفحة العودة (confirmPaymentOnReturn) ومهمة مجدولة تسأل المزوّد (reconcilePendingPayments)، وكلاهما عبر apply_payment_event الآمن للتكرار.
  4. شاشات الدفع: ملخص الطلب، اختيار الطريقة، التحويل لصفحة المزوّد، ثم نجاح أو إعادة محاولة.
  5. إصلاح: المزوّد يرجع النطاق demo.MyFatoorah.com فرفضته القاعدة، فاستُخدم new URL().href.
  6. إصلاح الأخير (من فحص الفيديو): المزوّد يعيد العملة KD بينما نخزّن KWD، فاعتُبرت الدفعة الناجحة غير مطابقة وعُزلت وبقي الطلب «بانتظار الدفع». وُحِّدت العملة وأُعيدت معالجة الدفعة، فصارت «مدفوعة» وصدر الإيصال وتحوّل الطلب إلى «تم الاستلام».
  7. شاشة النجاح فيها الآن زر العودة للرئيسية وزر متابعة الطلبات، وشاشة الفشل فيها إعادة المحاولة.
  8. مسارات /api/payments/webhook و/api/payments/reconcile و/api/submissions/scan.
